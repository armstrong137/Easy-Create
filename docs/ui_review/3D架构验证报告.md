## 1. 清单 §3.2 九问逐答

### 1.1 最终采用哪套 3D 方案？

**分三层表述（这就是结论，不是选项罗列）：**

1. **P2~P6 正式接入（现在就用）：WebView + three.js r147，资产离线打包**。
   本 Demo 即该路线的端到端实证。
2. **中期迁移目标（锁定，不另起炉灶）：flutter_scene（Impeller/flutter_gpu）**。
   它是纯 Dart 场景图引擎、与本项目技术栈同构（无 JS 桥、无 WebView 进程）、
   由 Flutter 核心成员维护（0.18.1，2026-06 发版，215 赞）。
   **今天不能用的唯一原因**：其 README 明确要求 Flutter master 渠道
   （依赖实验性 flutter_gpu / Native Assets；pubspec 写 >=3.44.0 只是为了 pub.dev 评分）。
   等 flutter_gpu 进 stable 即迁移，迁移面收敛在"场景层"一个模块。
3. **不采用**：Unity as Library（30MB+ 包体、商业授权、双端桥接重，对"单主角星球"
   场景是大炮打蚊子）；Thermion/Filament（最近一版 2025-09，维护信号弱于 flutter_scene，
   且同样要做原生桥接，性价比不如等 flutter_scene）。

为什么 WebView 路线能满足"极致 3D"：three.js 是全功能场景图引擎
（PBR 材质、法线/环境贴图、粒子、骨骼动画、后处理），表现力上限远高于
当前 FragmentShader；清单 §1.3 对它的四条风险（体验/手势/性能/离线资源）
本 Demo 已逐条给出实证或缓解方案（见 1.3~1.9）。

### 1.2 Flutter 和 3D 层如何通信？

已在 Demo 实证双向通道（延迟均在单帧级）：

- **Flutter → JS**：`WebViewController.runJavaScript('demoZoom(0.62)')`
  ——按钮驱动镜头推拉即走此通道。正式接入时暴露一个窄接口
  （`setSpin(能量转速)`、`setPlanet(纹理组)`、`cameraTo(镜头位)`），
  Riverpod 状态变化 → 单向下发。
- **JS → Flutter**：`addJavaScriptChannel('FlutterBridge')`
  ——Demo 每 0.5s 上报 `{fps, dist}` 并实时显示在 Flutter 胶囊上。
  正式接入时用于点击星球回调（镜头推进后进大纲页）、性能遥测。

### 1.3 资源如何加载？

**App 内置 127.0.0.1 回环静态服务**（`dart:io HttpServer` 从 rootBundle 供资产，
约 40 行，见 Demo `main.dart`）。这是本次验证发现的关键坑及其解法：

- ❌ `loadFlutterAsset`（file:// origin）下 WebGL `texImage2D` 被同源策略拦截
  （logcat 实录：`Access to image ... blocked by CORS`），页面能跑但纹理全黑；
- ✅ 回环 HTTP 后五张纹理全部加载成功（console 实录"纹理OK×5"）。
  完全离线、不占权限、不暴露端口（仅 loopback）；Android 需
  `usesCleartextTraffic="true"`（或 networkSecurityConfig 仅放行 localhost），
  iOS 需 ATS `NSAllowsLocalNetworking`。

### 1.4 页面生命周期如何暂停/恢复 3D？

- 页面不可见（PageView 切走/路由压栈/App 退后台）时：
  Flutter `AppLifecycleListener` + 路由感知 → `runJavaScript('pauseRender()')`
  停掉 rAF 循环；恢复时 `resumeRender()`。JS 侧 10 行。
- WebView 自身在 App 退后台时 Chromium 也会节流 rAF，双保险。
- 星球切换（多本小说）：单 WebView 复用 + `setPlanet()` 换纹理组，
  不销毁重建（首次建 WebView ~1s，复用切换 <100ms）。

### 1.5 Android / iOS 差异如何处理？

- 双端同用 `webview_flutter`（Android=Chromium WebView，iOS=WKWebView），
  three.js 代码零差异；WKWebView 的 WebGL 硬件加速默认开启。
- 差异点仅两处：明文回环许可（见 1.3）各配各的；
  iOS 上 platform view 合成走 UiKitView，Flutter 叠层同样支持（社区大量先例）。
- iOS 侧完整复验列入 P2 验收门（本机无 iOS 构建环境）。

### 1.6 包体积预计增加多少？

实测 Demo 增量 ≈ **2.7MB**（three.min.js 594KB + 五层地球纹理 2.08MB + Dart 侧代码可忽略；
webview_flutter 走系统 WebView，不带引擎）。五颗星球全套纹理按同规格估算 +8~10MB，
可用 LOD（近景 4K/常态 2K）与 basis 压缩再砍半。对比：Unity 路线 +30MB 起步。

### 1.7 低端机如何降级？

Demo 已内置三个旋钮，正式接入时由设置页/设备检测驱动：

- `renderer.setPixelRatio` 封顶（Demo 已用 1.75，低端降 1.0）
- 球体分段 64→32、粒子 2920→800、关闭云层壳
- 终极降级：整个 WebView 场景层换回现有 `planet.frag` 星球（保留旧实现正是为此）

### 1.8 性能数据与真机门禁

- 模拟器实测 2~5 fps，**根因已定位并留证**：logcat 实录
  `GL_RENDERER: Android Emulator OpenGL ES Translator (Google SwiftShader)`
  ——模拟器 WebView 的 WebGL 落在软件渲染，不代表产品性能。
- **✅ 真机门禁已通过（2026-07-09，用户 iPhone 实测）**：
  - 测法：Demo 场景页经局域网（iPhone 热点）由 Safari 打开——
    Safari 与 App 内 WKWebView 同为 WebKit 引擎，性能等价；
    页内 FPS 角标实时读数，用户实操截图三张为证。
  - 结果：**静置 60fps / 拖拽旋转 60fps / 双指缩放推近地表 60fps**，
    全程满帧（门禁线 静置≥55 / 交互≥40，大幅超过）；
    双指捏合、拖拽惯性手势在真手指下工作正常。
  - 顺带发现并修复：竖屏水平视场窄导致初始整球被左右裁切
    → 初始镜头距离改按视口宽高比自适应（fitDistance）。
  - 遗留：Android 真机（用户无安卓机）与 App 内 WKWebView 合成开销
    留待 P2 接入后首轮真机验收一并复核；WebGL 场景本体性能已无疑问。

### 1.9 如果 3D 集成失败，回退方案是什么？

按序回退，每级都可独立交付：

1. WebView 真机性能不达标 → 降级旋钮全开（1.7）再测；
2. 仍不达标 → 换 Thermion/Filament 做同规格 spike（资产直接复用）；
3. 引擎路线全部受阻 → 现有 FragmentShader 星球 + 增强
  （多层视差云影/更强大气）作为保底，改造重心移到清单其余模块
  （魔树/魔毯/卡堆的多层伪 3D 不依赖 3D 引擎）。

## 2. 本次验证暴露的工程事实（后续开发须知）

1. **WebGL 纹理必须走 HTTP（回环服务），不能 file://**——已封装在 Demo `main.dart`。
2. 模拟器 WebView WebGL = SwiftShader 软渲染，**一切 3D 性能结论只认真机**。
3. 云层贴图转黑底 JPG + 加色混合，比 RGBA PNG 小 90% 且视觉等价。
4. 8K 地表贴图（128MB 显存）超出移动端合理预算，4K 是甜点（Demo 实测细节足够）。
5. three.js r147 是最后一个 UMD 版本（r148 起纯 ESM），锁死 r147 直至迁移 flutter_scene。
