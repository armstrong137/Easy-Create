# 魔树全面复盘与整改计划

依据用户2026-11-01要求，本计划替代此前以根系、树皮逐项微调推动整体交付的方式。已清除的自动目标不重新创建。现有未提交根系候选保留为实验，不视为发布结果。

## 一、当前真实状态

- 远程已提交版本f56021e：连续二维魔树成为默认入口，真实main.dart不带实验参数构建通过；74项相关Flutter测试、静态分析和30章完整浏览器流程通过，含手机/宽屏、18次小节点击、历史、触摸、刷新及改名持久化。这不是全项目所有测试通过，也不是实体手机验收。
- e4a19e4已有100/1000章逐章历史和交互证据，修复旧CanvasKit路径副本增长问题。该高规模流程当时显式开启镜头，不能冒充最新无开关千章验收。
- 当前未提交根系候选：75项相关测试和Web构建通过；中间版本浏览器无错误但短根成钩，视觉拒绝，之后已修正。最后修正版尚未完成完整浏览器回归，不得上传为完成版。
- 视觉未通过：根颈与根盘缺少自然体积，树皮和叶片细节显得杂碎、偏亮，枝干与叶簇缺少参考中的整体层次。近景牌面虽能命中，但树体、装饰牌框与界面仍需统一观感。具体视觉判断以参考和实际截图并排审查，不由测试数量决定。
- 性能尚有差距：已提交默认版本成熟成长录像p95约25.1ms，上一轮1000章新增约50.1ms；仅是桌面浏览器采样，不证明手机流畅。

## 二、复盘

1. 成功标准失衡。工程测试证明坐标、数据和交互正确，却长期没有一个整体验收通过的视觉基准。工作不断完成，但用户看到的核心画面没有同步改善。
2. 局部调参替代整体设计。根尖、根盘、树皮和冠形分别修补，容易产生新的平切边、钩根、纹理噪声；没有先验证统一的造型与材质方案。
3. 集成顺序错误。视觉样件没有证明技术路线能达到参考，就持续接入页面、追性能、做高规模全量回归，返工成本过高。正式默认切换也早于整体视觉完成，入口验收不等于产品完成。
4. 计划缺少淘汰机制。同一类问题多轮仍不理想时，继续增加参数和测试，没有明确切换方案的门槛。
5. 进度表达不够聚焦。测试数、提交和验收日志过多，容易掩盖“用户要的画面仍未做好”。维护者应对这一推进方式负责，不能归因于用户没有继续补需求。

## 三、五步整改及出口

| 步骤 | 交付物 | 进入下一步的条件 |
|---|---|---|
| 1. 冻结基线并收敛要求 | 当前正式版、未发布实验、参考图并排的问题清单；一份唯一验收表 | 明确每处差距、保留功能、需要重做的视觉层；旧记录保留为历史，不能继续作为互相冲突的当前要求 |
| 2. 先完成整树视觉样件 | 同一方案的幼苗、中龄、成熟、近景四张实图，以及连续成长短片；统一树形、根颈、树皮、叶簇、枝牌 | 整体与局部均对照参考，不能靠缩小全景隐藏近景问题；静帧和成长同时成立，再集成。两轮完整样件仍失败就否决该造型/材质方案，重新评估实现方法，不继续无限调单个参数 |
| 3. 集成视觉层 | 通过样件的树体和枝牌进入正式大纲；保留数据库、仓库和已验证坐标契约 | 树龄与历史解耦，真实母枝接合，转屏和成长中间帧遮罩/热区一致；禁止成年树缩放、阶段换图冒充成长 |
| 4. 统一验收性能与交互 | 固定设备、构建、画布和录像条件的对照报告；30/100/1000章与手机/宽屏流程 | 普通规模以接近60帧为优化目标，高规模无崩溃或持续内存增长；记录实际帧时间及限制。桌面移动视口与实体手机分开结论；未测项目明确未验收，不用JS定时器单独证明绘制帧率 |
| 5. 整体交付审查 | 默认无开关版本、源码提交、验收截图/视频及逐项完成表 | 将最终版本与参考并排，核对造型、材质、成长、枝牌、历史、命中、性能；每项有当前证据。全部完成才结束，不能再用单个修补单元代表整体交付 |

## 四、执行约束

- 保留本机开发、验证后中文提交并推送的方式。完成的源码单元更新代码地图；未验证候选单独保留，不混入已完成版本。
- 沿用已确认的二维材质与空间动效、空书完整树苗、成熟宽冠古树；不要求用户再次选择已确定方向。
- 全面整改不等于全项目推倒重写。优先复用数据、仓库、历史和命中机制，重审造型生成、材质表现及两者配合；其他页面不扩功能。
- 每次更新只说明：本步交付物、与参考相比哪里改善、哪里仍失败、下一步出口。失败如实记载，不新增模糊的“继续打磨”阶段。
- 后续第一项工作是第1步的基线对照与验收表，然后第2步整树样件；不是继续完成原根系微调队列。本文件是整改方案，不宣称五步已执行完成，也不承诺未经验证的工期。
